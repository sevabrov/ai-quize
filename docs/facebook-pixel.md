# Facebook (Meta) Pixel

Піксель потрібен не для реклами як такої, а щоб побачити **bottleneck**: на
якому саме кроці люди зникають. Квіз - SPA без переходів по URL, тому сам по
собі Events Manager побачив би один `PageView` і нічого більше. Тому кожен крок
сценарію надсилається окремою подією.

## Налаштування

Pixel ID лежить прямо в коді - `pixelId` у `src/lib/env.ts`. Змінної оточення
немає навмисно: ID не таємниця (він однаково видно в бандлі кожному
відвідувачу), тож ділити його між `.env`, `.env.example` і секретами CI - зайва
робота й зайве джерело помилок.

Поточний піксель - веб-набір даних **QUIZ**, ID `922808357198809`.

Якщо потрібен інший піксель:

1. Events Manager → **Наборы данных → Подключить данные → Веб → Meta Pixel**.
2. Скопіювати **ID пікселя** (15-16 цифр) з картки набору даних. Важливо: набір
   даних для мобільного застосунку теж має ID, але він підписаний **ID
   приложения** - `fbq('init')` його мовчки відкидає, і жодного запиту на
   `/tr` не буде.
3. Замінити значення `pixelId` у `src/lib/env.ts`.

**Порожній рядок = піксель вимкнено**: скрипт Meta не вантажиться взагалі, а
`track()` стає no-op. Так можна тимчасово прибрати тестові проходження зі
статистики замовника.

## Події

Порядок у таблиці = порядок воронки. Стандартні події Meta (`Lead`, `Schedule`…)
дублюють кастомні там, де крок має сенс як конверсія для реклами.

| Подія                | Коли                                        | Параметри              |
| -------------------- | ------------------------------------------- | ---------------------- |
| `PageView`           | завантаження сторінки                       | -                      |
| `QuizStart`          | натиснула «Почати» на інтро                 | -                      |
| `QuizAboutSubmitted` | відповіла на відкрите питання «про себе»    | -                      |
| `QuizQuestionsStart` | перейшла з екрана «про себе» до питань      | -                      |
| `QuizAnswer`         | **кожна** відповідь на питання              | `question`, `step`, `total`, `option` |
| `QuizComplete` + `CompleteRegistration` | остання відповідь, діагностика пройдена | `profile` |
| `AnalysisRequested` + `Lead` | натиснула «Хочу аналіз»             | `profile`              |
| `AnalysisDelivered`  | дочекалась кінця 3-хвилинного очікування    | -                      |
| `BookingOpened` + `InitiateCheckout` | натиснула «Хочу на розбір»  | `profile`              |
| `BookingConfirmed` + `Schedule` | Cal.com підтвердив бронювання    | -                      |
| `MihiClick`          | клік по партнерському блоку MIHI            | -                      |
| `QuizExit`           | натиснула «Вийти»                           | `stage`, `step`        |

Ключова для аналізу - `QuizAnswer`: у Events Manager її можна розбити за
параметром `step` і побачити спад між питаннями. `AnalysisDelivered` проти
`AnalysisRequested` показує, скільки людей не дочекались трьох хвилин.

## Перевірка

1. Розширення **Meta Pixel Helper** для Chrome - показує ID і кожну подію
   в реальному часі.
2. Events Manager → вкладка **Test events** - там видно події з параметрами.
3. Без розширення: DevTools → Network → фільтр `facebook.com/tr` - по одному
   запиту на подію.

Якщо подій немає взагалі, у консолі `window.fbq.callMethod` відповість, де саме
рветься ланцюжок:

- `undefined` - `fbevents.js` не завантажився: блокувальник реклами або порожній
  `pixelId`. Накопичене видно в `window.fbq.queue`.
- функція Meta, але запитів на `facebook.com/tr` немає - ID неправильний
  (типовий випадок: узяли ID застосунку замість пікселя). Помилку видно
  в консолі на рівні **Default levels**: `Invalid PixelID`.

## Що врахувати

- Блокувальники реклами ріжуть піксель у частини аудиторії, тому абсолютні
  цифри будуть нижчі за реальні. Для пошуку bottleneck це не страшно -
  важливі **співвідношення** між кроками, а не абсолют.
- Персональні дані (текст «про себе», відповіді у вільній формі, e-mail з
  Cal.com) у події **не** передаються - тільки номери кроків і id профілю.
  Повні дані лишаються в Google Таблиці.
- Події прив'язані до дій користувача, а не до `useEffect` на стані, тому F5 на
  екрані результату не надуває конверсію повторними спрацюваннями.
